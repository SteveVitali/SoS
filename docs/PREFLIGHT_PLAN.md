# Pre-flight Clarification & Planning for Create PR Jobs

## Overview

Before executing a `create_job`, the system can optionally run a **pre-flight phase**: a repo-aware planning session using Claude Code CLI, followed by explicit user confirmation. The LLM router decides whether a task warrants this (complex/ambiguous tasks get it; simple ones skip straight to execution).

## Design Decisions

- **Option A** — inject active proposal state into thread/conversation context; the routing LLM naturally handles multi-turn clarification
- **Repo-aware planning** — Claude Code CLI reads the codebase in a read-only session to produce a concrete technical plan
- **Explicit confirmation** — user must affirmatively approve before execution begins
- **No expiration** — proposals stay in `PENDING_CONFIRMATION` indefinitely
- **Simple tasks skip** — the LLM router decides; trivial requests go straight to `create_job`

## Architecture

### New Job Statuses

```
PLANNING → PENDING_CONFIRMATION → QUEUED → RUNNING → ... (existing flow)
```

Add to `JobStatus` enum in `src/shared/types.ts`:
- `PLANNING` — worker is running a read-only Claude Code session to generate a plan
- `PENDING_CONFIRMATION` — plan has been generated and presented to the user; awaiting explicit "go"

Both are non-terminal. `PLANNING` is an active status (worker holds a lease). `PENDING_CONFIRMATION` is passive (no worker lease — similar to `WAITING_FOR_APPROVAL`).

## Execution Flow

### Happy Path (Complex Task)

```
1. User: "@steve implement OAuth2 PKCE flow for mobile clients"
2. routeMessage() → LLM returns plan_job { task_text: "Implement OAuth2 PKCE..." }
3. executeCommand() → createJobFromSlack() with status: "PLANNING"
4. Steve replies: "I'll analyze the codebase and put together a plan. Hang tight."
5. Worker polls, claims the PLANNING job
6. Worker: resolve repo → acquire worktree → runClaudePlan() → release worktree
7. Worker posts plan via api.submitPlan() → job moves to PENDING_CONFIRMATION
8. Server posts plan to Slack thread / web chat:
   "Here's my plan:
    1. Add PKCE challenge generation in src/auth/pkce.ts
    2. Modify OAuth flow in src/auth/oauth.ts to support code_challenge
    3. Add mobile-specific token storage adapter
    4. Update tests in src/auth/__tests__/
    Reply 'go' to confirm, or ask questions."
9. User: "looks good, go"
10. routeMessage() → LLM sees PENDING_CONFIRMATION job in context → confirm_job
11. executeCommand() → job moves to QUEUED
12. Worker picks up, runs normal runJob() flow
```

### Happy Path (Simple Task — Skips Planning)

```
1. User: "@steve fix the typo in README.md line 42"
2. routeMessage() → LLM returns create_job (simple task, no planning needed)
3. Normal existing flow — immediate QUEUED → execution
```

### Multi-Turn Clarification Before Planning

```
1. User: "@steve add caching to the API"
2. routeMessage() → LLM returns chat { response: "Which endpoints? Redis or in-memory? TTL?" }
3. User answers questions in thread
4. routeMessage() → LLM (with full thread context) returns plan_job with refined task_text
5. ... continues as happy path
```

Note: The LLM can use `chat` to ask clarifying questions *before* even creating the planning job. This is free-form and doesn't require any new infrastructure — it already works today. The `plan_job` tool is only invoked once the task is clear enough to plan against the codebase.

### User Requests Plan Changes

```
1. Plan posted to user
2. User: "can you also add refresh token rotation?"
3. routeMessage() → LLM sees PENDING_CONFIRMATION job → responds as chat
   "Noted — I'll include refresh token rotation. Want me to regenerate the plan, or just go with it?"
4a. User: "just go" → confirm_job (revised_task_text includes the addition)
4b. User: "regenerate" → could cancel + re-plan, or a dedicated re-plan action
```

For v1, option 4a is sufficient. Re-planning can be modeled as cancel + new plan_job.

## Worker-Side Changes

### New Function: `runClaudePlan` in `src/worker/executor/claude.ts`

```typescript
export async function runClaudePlan(
  worktreePath: string,
  taskText: string,
  repo: RepoEntry,
  threadContext?: string,
  attachments?: JobAttachment[],
  abortSignal?: AbortSignal,
): Promise<ClaudeResult>
```

Uses a **planning-specific prompt** and **restricted tool access**:

```typescript
const prompt = [
  "# Planning Mode",
  "",
  "Analyze the codebase and produce a technical implementation plan for the following task.",
  "Do NOT make any code changes. Do NOT create, modify, or delete any files.",
  "",
  "## Task",
  taskText,
  "",
  // ... repo info, thread context, attachments (same as buildPrompt) ...
  "",
  "## Instructions",
  "1. Read relevant source files to understand the current architecture",
  "2. Identify which files need to be created or modified",
  "3. Outline the specific changes needed in each file",
  "4. Note any risks, edge cases, or design decisions that need input",
  "5. Estimate complexity (small / medium / large)",
  "",
  "Output a concise, numbered implementation plan. Be specific about file paths and function names.",
  "Keep it under 500 words.",
].join("\n");
```

CLI invocation — use `--allowedTools` to restrict to read-only operations:

```typescript
return runClaudeProcess(
  [
    "claude",
    "-p", promptPath,
    "--output-format", "stream-json",
    "--verbose",
    "--allowedTools", "Read,Grep,Glob,LS,Bash(find:*),Bash(cat:*),Bash(head:*),Bash(tail:*)",
  ],
  worktreePath,
  logPath,
  10 * 60 * 1000, // 10 min timeout (planning should be fast)
  abortSignal,
);
```

Note: `--dangerously-skip-permissions` is deliberately **not** used — we use `--allowedTools` to whitelist only read operations. This ensures the planning session cannot modify the repo.

### New Function: `runPlanJob` in `src/worker/executor/runPlanJob.ts`

```typescript
export async function runPlanJob(
  job: JobDoc,
  workerId: string,
  config: WorkerConfig,
  api: WorkerApiClient,
  leaseSignal?: AbortSignal,
): Promise<void> {
  // 1. Resolve repo (same as runJob steps 1-2)
  // 2. Acquire worktree slot
  // 3. Fetch Slack thread context (same as runJob step 3)
  // 4. Run runClaudePlan() — read-only Claude session
  // 5. Extract plan from Claude output
  // 6. Call api.submitPlan(taskId, workerId, { plan_summary, metrics })
  //    → server moves job to PENDING_CONFIRMATION, posts plan to Slack/chat
  // 7. Release worktree slot (important: don't hold it during confirmation wait)
}
```

Key difference from `runJob`: the worktree is **released immediately** after planning. The job doesn't hold resources while waiting for confirmation.

### Worker Dispatch Update (`poller.ts`)

```typescript
function dispatchJob(job, workerId, config, api, leaseSignal) {
  if (job.status === "PLANNING") {
    return runPlanJob(job, workerId, config, api, leaseSignal);
  }
  if (job.job_type === "respond_to_pr_comments") {
    return runRespondToComments(job, workerId, config, api, leaseSignal);
  }
  return runJob(job, workerId, config, api, leaseSignal);
}
```

### Pollable Statuses Update (`jobRepo.ts`)

Add `PLANNING` to the pollable statuses in `findPollableJobs()`:

```typescript
$or: [
  { status: "QUEUED" },
  { status: "PLANNING" },  // ← new
  { status: { $in: ["RUNNING", "FIXING_CI"] }, lease_expires_at: { $lt: now } },
]
```

Actually — `PLANNING` jobs should be created as `QUEUED` initially and transition to `PLANNING` when claimed, just like `QUEUED` → `RUNNING`. This avoids changing the poll query. The worker recognizes it's a planning job by checking a flag on the `JobDoc`.

**Revised approach**: Add a boolean field `needs_plan: true` to the job doc. Jobs with `needs_plan` are created as `QUEUED` like normal. When the worker claims it:
- If `needs_plan && !plan`, run planning flow → submit plan → job goes to `PENDING_CONFIRMATION`
- If `!needs_plan` or already has a plan (confirmed), run normal execution flow

This keeps the polling/claiming infrastructure completely unchanged.

### New API Endpoint: `POST /api/worker/jobs/:id/submit-plan`

### New API Endpoint: `POST /api/worker/jobs/:id/confirm`

Or, this can be a server-side-only operation (not worker API) since confirmation comes from the user via Slack/web, not from a worker.

```typescript
// In jobService.ts:
export async function confirmJob(taskId: string, revisedTaskText?: string): Promise<JobDoc | null> {
  // 1. Verify job is PENDING_CONFIRMATION
  // 2. Set status = "QUEUED", clear needs_plan flag (or set plan_confirmed = true)
  // 3. Optionally update task_text if revisedTaskText provided
  // 4. Return updated job (workers will pick it up on next poll)
}
```

### `commandExecutor.ts` — New Cases

```typescript
case "plan_job": {
  // Same as create_job, but set needs_plan: true on the job doc
  const job = ctx.source === "slack" && ctx.slack
    ? (await createJobFromSlack({ ...args, needs_plan: true, ... })).job
    : await createJobFromWeb({ ...args, needs_plan: true });
  return {
    reply: `${reply}\n\n📋 Planning task: \`${job.task_id.slice(0, 8)}…\` — I'll analyze the codebase and propose a plan.`,
    actionTaken: `plan_job ${job.task_id}`,
    taskId: job.task_id,
  };
}

case "confirm_job": {
  const taskId = await resolveTaskId(args.task_id || "");
  if (!taskId) return { reply: "...", actionTaken: "confirm_job: not found" };
  const job = await findJobByTaskId(taskId);
  if (job?.status !== "PENDING_CONFIRMATION") {
    return { reply: "...", actionTaken: "confirm_job: wrong status" };
  }
  await confirmJob(taskId, args.revised_task_text);
  return {
    reply: `${reply}\n\n✅ Plan confirmed — executing \`${taskId.slice(0, 8)}…\``,
    actionTaken: `confirm_job: ${taskId}`,
    taskId,
  };
}
```

## Edge Cases

- **User cancels during planning**: existing cancel flow works — `PLANNING` is an active status, cancel sets `CANCELED`
- **User cancels during confirmation wait**: same — `PENDING_CONFIRMATION` can transition to `CANCELED`
- **Worker crashes during planning**: lease expires, job goes back to `QUEUED`, another worker picks it up and re-plans
- **Multiple plan_job for same thread**: the LLM should see the existing `PENDING_CONFIRMATION` job in context and use `confirm_job` instead. If a new one gets created, it's a separate job — no conflict.
- **Confirmed job re-acquires worktree**: the worktree was released after planning. On re-claim, `runJob()` acquires a fresh slot. The repo is already cloned (from the planning phase), so `ensureClone` is a no-op.
- **Plan injected into execution prompt**: when `runJob()` detects `job.plan?.summary`, it passes it to `buildPrompt()` as additional context so the execution Claude session has the benefit of the analysis without re-reading everything.
